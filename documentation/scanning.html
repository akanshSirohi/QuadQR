QUADQR DOCUMENTATION

Scanning & Camera

The complete browser/image/camera scanner guide, including every supported scanner tuning option and every progressive recovery control.

Need a specific option?

Every scanner option is defined on this page. The Configuration Reference also collects scanner, encoder, renderer, security, benchmark, and Node.js options in one searchable index.

Scanner pipeline#

finder detection→perspective geometry→RGBW / Triangle16 sampling→color calibration→Spectrum ECC 2.0→CRC→payload

The normal path is deliberately cheap. Recovery stages only activate after a normal decode misses. That distinction is important when tuning camera cadence options: a lower cadence number spends more CPU on difficult frames, not on frames that already decode cleanly.

Scan an uploaded browser image#

JS
import { scanFile } from "quadqr-js/browser";

const result = await scanFile(file, {
  debug: true,
  includeRectified: true
});
console.log(result.text);

scanFile() decodes the browser File into RGBA pixels and then uses exactly the same scanImageData() pipeline described below.

Live camera scanning#

JS
import { startCameraScanner } from "quadqr-js/browser";

const scanner = await startCameraScanner(video, {
  scanInterval: 33,
  multiFrame: true,
  cameraFinderRecoveryEvery: 2,
  cameraAutoColorEvery: 1,
  cameraHighResolutionRecovery: true,
  onResult(result, frameMeta) {
    console.log(result.text, frameMeta);
  }
});

// Later:
scanner.stop();

The returned controller contains stream, video, stop(), and scanNow(). By default the scanner stops on the first successful decode.

Core live-camera controls#

The live scanner is frame-driven on browsers that support requestVideoFrameCallback() and does not queue stale fast-path frames. Supported browsers use a dual-worker engine: a fast worker continuously handles fresh normal finder/geometry/decode attempts while a second worker runs the complete perspective, precise-alignment, QuadQR Auto Color, QR-region enhancement, Spectrum ECC, multi-frame, and damaged-code recovery stack independently. A difficult recovery frame therefore cannot hold the camera scheduler hostage. Finder detection itself remains JavaScript. WASM accelerates grayscale/Otsu/binary preprocessing and CRC beneath the same detector. The visible camera crop is resized to the normal scan dimension before worker transfer, reducing mobile bitmap and memory pressure. Unsupported or CSP-restricted environments automatically use the same full scanner on the main thread.

Progressive camera recovery#

After a miss, the scanner increases effort in bounded stages. The *Every options are cadence controls measured in missed scan cycles. They are performance knobs, not millisecond timers.

cameraFinderRecoveryEvery example

Default 2 means finder recovery is eligible on the first retry after a miss, then every other missed cycle. 1 runs it on every missed cycle. 4 uses it much less often, reducing CPU but potentially delaying recovery when lighting or perspective is difficult.

How the recovery sequence behaves#

  1. Fresh fast scan: a 640 px visible ROI is immediately checked for normal finder geometry, calibrated sampling, ECC, and CRC.
  2. Parallel recovery dispatch: finder evidence controls whether the independent full-recovery worker receives a fresh frame. Two or more finders trigger immediately; one finder must persist; zero-finder scenes stay fast-only.
  3. High-resolution geometry retry: the recovery worker can use up to 960 px when dense modules need more pixels.
  4. QuadQR Camera Auto Color crops: progressively QR-centric histogram windows remain available for strong yellow/warm casts.
  5. QR-region enhancement: if geometry is strong, enhance only the rectified code area.
  6. Multi-frame fusion: combine compatible high-confidence observations and retry Spectrum ECC 2.0.

Multi-frame confidence fusion#

Fusion is not simple majority voting. Each cell vote is weighted by source confidence, frame quality, and recency. Second-best cell hypotheses contribute weak evidence. Before frames are fused, high-confidence data-cell agreement is checked so two different QuadQR symbols of the same version do not contaminate each other.

Camera callbacks and frame metadata#

onResult and onDecode receive the same successful decode plus frame metadata. onDiagnostic receives live attempt events. Full field definitions are in Configuration Reference → Camera callback payloads.

Understanding scanner confidence#

Successful image scans include an overall confidence plus geometry, calibration, structure, and ECC-related diagnostics. Confidence is a ranking/debug aid, not a cryptographic guarantee. Payload acceptance still requires Reed-Solomon validation and the final CRC.

Secure and signed scans#

A secure result can be geometrically and cryptographically intact while still returning text: null. Use decryptDecoded() with the password or raw key. Signed payload verification is separate: call verifyDecodedSignature() with a trusted Ed25519 public key or trusted-key registry.

Reliability testing#

Use runReliabilityLab(), runPerspectiveSweep(), and assessScanability() to test scanner behavior under blur, lighting shifts, downscaling, and 3D perspective before shipping a physical workflow.
